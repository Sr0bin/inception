# Inception

## Description

Inception is a system administration project: a small web infrastructure built
with Docker Compose inside a virtual machine. Three services, each in its own
container built from `debian:bookworm` (the penultimate stable Debian):

| Service     | Role                                                        |
|-------------|-------------------------------------------------------------|
| `nginx`     | Single entrypoint, HTTPS only on port 443 (TLSv1.2/TLSv1.3) |
| `wordpress` | WordPress + php-fpm (FastCGI on port 9000, no web server)   |
| `mariadb`   | WordPress database (port 3306, internal network only)       |

```
 client ──443/TLS──> nginx ──9000/FastCGI──> wordpress ──3306──> mariadb
                       │                        │                   │
                       └──── wordpress volume ──┘     mariadb volume┘
                         (/home/rorollin/data/wordpress)  (/home/rorollin/data/mariadb)
```

### Use of Docker and sources

- `Makefile`: generates missing secrets, creates the data folders, runs
  `docker compose up -d --build`.
- `srcs/docker-compose.yml`: services, the `inception` bridge network, the two
  named volumes, the Docker secrets.
- `srcs/.env`: non-confidential configuration (domain, db name, user names).
- `secrets/`: passwords (git-ignored, generated by `make` if missing).
- `srcs/requirements/<service>/`: one `Dockerfile` per service, its `conf/`
  files and its `tools/` entrypoint script.

### Main design choices

- **No ready-made images**: everything is installed with `apt` on top of
  `debian:bookworm`; the image names (`nginx:inception`, ...) match the
  services and never use the `latest` tag.
- **PID 1**: every container ends on the real daemon in the foreground
  (`nginx -g 'daemon off;'`, `php-fpm8.2 -F`, `mysqld`). Entrypoint scripts
  do their setup and then `exec` the daemon, so it receives the
  signals sent by `docker stop`. No `tail -f`, `sleep infinity` or loops.
- **Startup order**: mariadb has a `healthcheck` (`mysqladmin ping`) and
  wordpress uses `depends_on: condition: service_healthy`, so no wait loop is
  needed in the scripts.
- **Idempotent setup**: MariaDB applies its SQL through `--init-file`
  (`CREATE ... IF NOT EXISTS`); WordPress checks each step separately (files
  downloaded, `wp-config.php` created, site installed, second user created)
  and only runs the missing ones. Restarting never breaks or duplicates anything.
- **Restart policy**: `unless-stopped`, containers come back after a crash.
- **TLS**: a self-signed certificate is generated at build time;
  `ssl_protocols TLSv1.2 TLSv1.3;`.

### Virtual Machines vs Docker

A VM emulates a full machine and boots its own kernel: strong isolation, but
heavy (GBs, slow boot). A container is an isolated process sharing the host
kernel (namespaces + cgroups): lightweight, starts in milliseconds, one
service per container. Here the VM provides the host, Docker isolates services.

### Secrets vs Environment Variables

Environment variables are visible in `docker inspect`, in `/proc/<pid>/environ`
and are inherited by every child process. Docker secrets are files mounted in
`/run/secrets/` (read-only) only in the containers that declare them. So `.env`
holds non-sensitive config, and passwords are Docker secrets.

### Docker Network vs Host Network

With `network_mode: host` a container shares the host network stack: no isolation,
every port it opens is exposed. A user-defined bridge network gives containers
their own private network with DNS by service name (`wordpress`, `mariadb`);
only nginx publishes a port (443) on the host.

### Docker Volumes vs Bind Mounts

A bind mount maps an arbitrary host path into a container; it depends on the
host's layout and is not managed by Docker. A named volume is a Docker object
(`docker volume ls/inspect`), managed by Docker and referenced by name. Here
the named volumes use the `local` driver with `driver_opts` so their data is
stored in `/home/rorollin/data`, as required by the subject.

## Instructions

Prerequisites: a Linux VM with Docker Engine, the Compose plugin, `make`
and `openssl`.

```sh
echo "127.0.0.1 rorollin.42.fr" | sudo tee -a /etc/hosts
make            # build + start (generates secrets/ on first run)
```

Open <https://rorollin.42.fr> (accept the self-signed certificate).
Admin panel: <https://rorollin.42.fr/wp-admin>.

| Command       | Effect                                           |
|---------------|--------------------------------------------------|
| `make`        | build images and start the stack                 |
| `make stop`   | stop containers (keep them)                      |
| `make start`  | restart stopped containers                       |
| `make down`   | remove containers and network (data kept)        |
| `make fclean` | remove everything: containers, images, volumes, data |
| `make re`     | `fclean` then `all`                              |

See [USER_DOC.md](USER_DOC.md) and [DEV_DOC.md](DEV_DOC.md) for details.
